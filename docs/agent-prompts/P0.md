```text
/goal 完成 Japanese101 的 P0：建立唯一、可追蹤且可執行的開發基準，讓後續 agent 能依相同規格開發及驗收。依 project.md 與 tasks.md 實作、驗證及提交；只有全部 Phase 驗收通過才標 COMPLETE。

本 Phase 執行契約
前置條件：規劃文件已存在於本 checkout；本 Phase 沒有前置 Phase。先診斷 ENV-01，同時推進不依賴環境的文件工作。
任務範圍：ENV-01、P0-01～P0-07，共 8 項。

執行重點：
1. 盤點所有路由、feature、game_mode，對照 F-01～F-08 與舊規格，逐項決定保留、修復、合併或延後。
2. 建立 PRODUCT_DIRECTION.md、ROADMAP.md、UI_UX_SPEC.md、ENGINEERING_RULES.md、CONTENT_BLUEPRINT.md、ACCEPTANCE_MATRIX.md；引用 project.md 的共同規則，避免另建矛盾副本。
3. 產出 N5 能力圖、24 單元 manifest、14 類題型對照及題族規則。每項能力有先修、教學、練習與延後檢核。
4. 執行實際基準檢查與 Chromium／Firefox／WebKit smoke，保存操作與視覺證據；現有失敗要有 task，不能冒稱全綠。
5. 統一 CI 與正式部署入口；先依 repository 設定找證據。外部管理權限不足時不宣稱已變更成功。
6. 確認實際工程、內容審核、產品與 QA 負責人；已指定者沿用，未知者記錄待指派，不編造姓名。

完成門檻：project.md §3.1 的六項條件與 P0-07 全數通過。內容 blueprint 的人工審核、部署設定與實際責任人不能由 agent 虛構。
外部依賴：日語內容審核、責任人指派，以及工具無權調整的主機／GitHub／部署設定。
範圍邊界：不提前全面修復 P1 的產品問題；允許為本 Phase 驗證基準所必要的工具與 CI 修改。

專案：https://github.com/dannythreeka/Japanese101
本次 Phase：P0

你是本 Phase 的負責 agent。持續執行直到驗收完成，或所有可獨立推進的工作已完成且剩餘項目確實受外部條件阻擋。不要只提出計畫，也不要每完成一個 task 就詢問是否繼續。

一、啟動與範圍
1. 閱讀適用的 AGENTS.md、project.md、tasks.md，以及前一 Phase 的驗收與交接紀錄；遵守平台工具與權限規則。
2. 確認 checkout、基準 commit、未提交修改、執行環境與工具。以 repository 的版本及設定為準，不假設本機路徑或套件版本。
3. project.md 是產品與驗收基準；tasks.md 是 task、依賴與完成條件。prompt 的摘要不能取代這兩份文件。
4. 找出本 Phase 的全部 task，包括教材 Uxx 與模擬卷 MA／MB／MC；不可只依 Phase 前綴篩選。
5. 前置 Phase 必須有驗收通過的 commit 與證據，並包含在目前 checkout；不自行把前置依賴改成 DONE。
6. 文件缺失先查 repository、已知分支及交接資料。仍缺失時記錄阻礙，不杜撰原規格。
7. 同一時間由本 agent 負責本 Phase 的分支整合；本指令不要求另啟 sub-agent。若另有獲授權的平行工作，需隔離分支／worktree 並明確分配檔案，避免互相覆寫。

二、自主執行
1. 依 tasks.md 的依賴選取可執行 task，逐項檢查現況、實作、驗證、修復、更新紀錄並 commit。
2. 一般技術選型、程式整理、測試失敗及可逆實作決策自行處理並記錄理由，不向我確認。
3. 發現必要漏項時新增具體 task，包含 ID、原因、依賴、交付物與驗收；不藉機擴大產品範圍。
4. 不跨入下一 Phase，不降低驗收門檻；不以刪測試、放寬斷言、偽造資料或隱藏錯誤達成通過。
5. 遇到問題先重現與定位，再嘗試有證據支持的修正方案；相同失敗且條件未變時不無限重試。
6. 個別 task 受阻時，繼續其他無依賴的工作。僅以規劃完成、程式寫完或 build 成功，不足以結束本 Phase。

三、操作與視覺驗收
1. 實際啟動應用程式，使用可用的 Playwright 或 computer use 操作相關流程。
2. 按規格驗證主要流程、錯誤、離線、玩家隔離，以及本 Phase 的邊界情境。
3. UI 變更檢查規定的 viewport、鍵盤、縮放、操作尺寸及畫面狀態；保存 commit、環境、瀏覽器版本、步驟、結果與截圖／trace。
4. 實際檢視截圖並與 UI／UX 規範比對，不能以截圖產生成功代替視覺驗收。人工核准要求仍需真實審核者。
5. 瀏覽器模擬與實體裝置分開記錄；WebKit 模擬不能稱為實體 iPad Safari 驗收。
6. 未執行標 NOT_RUN，受阻標 BLOCKED，不填成 PASS。檢查的 commit 與最終交付 commit 若不同，要指出差異並重跑受影響檢查。
7. 人工教材審核、音訊審聽、家長同意、兒童試用只能使用實際完成紀錄；AI review 不取代人工簽核。
8. 使用隔離測試玩家與資料，不清空真實孩子的紀錄。證據不得包含憑證或可識別兒童的資料。

四、Git 與持續交接
1. 從本 Phase 的有效基準建立專用分支，保留既有使用者修改；不重設或覆寫他人工作。
2. 每個可驗證的小批次完成後 commit，訊息包含 task ID；不要累積整個 Phase 才保存。
3. 更新 tasks.md 狀態，建立或更新：
   docs/phases/P0/progress.md
   docs/phases/P0/acceptance.md
   docs/phases/P0/handoff.md
4. progress 記錄實際 owner、基準、當前 task、決策、失敗嘗試、阻礙與下一步；acceptance 逐項列 task／需求、預期、實際、證據及 reviewer；handoff 記錄可恢復的命令與未完成工作。
5. 上下文壓縮或重新開始後先讀交接，再從最新 commit 繼續；不可重做已驗收工作或遺漏待辦。
6. 已授權 commit、push 本次工作分支並建立 PR；未授權合併 main 或正式發布。完成前檢查 diff 只含本次相關修改。
7. push 失敗保留本機 commit 並記原因；沒有 commit SHA 不能宣稱已提交。文件、測試與驗收紀錄都要納入提交，較大 trace／影片可放既有 artifact 儲存位置並在文件引用。
8. PR 說明問題與結果、task ID、驗證及已知限制；工程未完成或缺外部驗收時維持 draft。

五、溝通、完成與阻擋
1. 不問「要不要繼續」，不重新確認已授權事項。一般進度寫入紀錄；平台要求進度訊息時僅簡短更新，不要求我回答。
2. task 只有所有驗收與必要 reviewer 確認完成才標 DONE；需要人工審核的項目可標 IN_REVIEW，缺外部資源標 BLOCKED。
3. Phase 只有全部 task、依賴與 gate 證據通過才標 COMPLETE；不得因接近用量上限而標完成。
4. 工程已驗證但缺人工審核／人測／實機證據時，可在 Phase 報告標 ENGINEERING_READY。這不是 task DONE，也不是整個 Phase 或完整 /goal 已完成；依賴未滿的下游 task 仍保留原狀態。
5. 缺重大產品決策、權限、帳號、設備或人員時，先完成所有不受影響工作，準備具體可審閱結果；確無可推進工作時集中回報一次最小解阻需求，不忙等、不繞過授權限制。
6. 遵循平台的 goal blocked／用量／中斷處理規則，不自行把外部等待誤標成成功。盡可能先保存進度與恢復步驟。
7. 不自行購買服務、對外招募或發送訊息；若需這類動作，先完成材料並列出待授權事項。

最終回報只包含：
- Phase 狀態：COMPLETE／ENGINEERING_READY／BLOCKED／IN_PROGRESS（用量或中斷時）
- 已完成及未完成 task ID
- commit／PR
- 驗收結果與證據位置
- 若受阻，解除阻礙所需的最小外部動作

現在直接開始執行。
```
